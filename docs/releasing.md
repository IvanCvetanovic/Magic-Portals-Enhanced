# From this repository to a release: the path, and the list for going public

Planning step 210 (PORT-12), brought up to date at planning step 211 (2026-11-03). One page. It gathers what [ci.md](ci.md) section 7 and [packaging.md](packaging.md) section 8 say, and adds what the maintainer does once, before the repository is public. **What has been done, plainly: the first release was made on 2026-11-03, steps 1 to 9 of the path below, for its Windows, Linux and Android files. Step 10 was not done, the macOS and iOS archives were not made, and the repository is still private.** `release.yml` was dispatched twice and its second run succeeded in all six jobs ([ci.md](ci.md) section 9). The Linux archive was unpacked and started in a Linux subsystem on the maker's own PC; the Windows archive has not been started anywhere, the Android APK has not been installed anywhere, and no archive has been tried on a PC that is not the maker's ([platforms.md](platforms.md) says which file was started where). `ci.yml` and `android-emulator.yml` have never been dispatched. Each step names the file that has its commands.

## The numbered path

1. **The version.** `project(MagicPortals VERSION x.y.z ...)` in the top-level `CMakeLists.txt` is the one definition (the first release was made at the number it holds today; whether a public release keeps it is the maintainer's). `python tools/package/check_version.py` must say `ok`; it names every place that disagrees. Done for the first release.
2. **The repository as a stranger sees it.** `python tools/ci/check_public.py` must print no ERROR ([ci.md](ci.md) section 8). Read its OWNER-FILE and RECORD-PATH lines too. Done for the first release.
3. **The release programs.** Dispatch `release.yml` with the version (Actions, *release.yml*, *Run workflow*; [ci.md](ci.md) section 2 says what it costs). It builds the Windows, Linux, Android (a debug-signed shell) and Apple programs and uploads them with `SHA256SUMS.txt` and `VERSIONS.txt`. **Done on 2026-11-03:** the first dispatch failed in its `windows` job (the runner image had no Vulkan loader), the runner image was changed, and the second dispatch built every program ([ci.md](ci.md) section 9).
4. **Download and check.** The artifact `release-programs`; `sha256sum -c SHA256SUMS.txt` before using anything in it. Done: the check over the artifact's files passed.
5. **The content package**, on the maintainer's PC, from the maintainer's own copy of the original. **Before assembling** (since the interface languages): (a) make the ten translations of the achievements, `python -I tools/l10n/make_achievement_languages.py` (it needs the gitignored `out/data/lang_src`; `--check` validates and writes nothing), so that the ten `out/data/achievements.<code>.json` exist: the closure ships an overlay only if it is there, and a package made from an incomplete `out/data` carries English-only achievements for that language without an error. (b) **REBUILD the content package**: `python tools/package/package.py content --repo <repository> --reference <reference folder> --out <content package>` ([packaging.md](packaging.md) section 3). The default package on this PC, `out/dist/content`, is an OLDER one of 883 files made before the languages, and holds none of what follows. (c) Check that the new package holds `port-data/lang/languages.json`, `port-data/fonts` (the 4 faces and their 4 licence texts) and the ten `tables/achievements.<code>.json`. At the last build it held 923 files, 26,968,736 bytes; those counts are examples, to be retaken at each build ([packaging.md](packaging.md) section 3 has the figures of another run). Done for the first release, which was made before the languages.
6. **Check, then assemble, one platform at a time** ([packaging.md](packaging.md) section 8 has every command):
   `release.py check-program <program> --platform windows|linux|macos|ios`, then `release.py assemble --platform windows|linux --program <program> --content <content package> --out <release folder>` and, for the Apple platforms, `--shell <the shell> --content <content package>`. The macOS seal is invalid once the data is inside; [apple.md](apple.md) section 7 has the three routes. **Done for the Windows and Linux archives** (from the programs CI built); the Apple archives with the game in them were not made.
7. **The Android release APK**, built on the maintainer's PC with the maintainer's own key (`tools/build_android.sh --release --keystore ... --data <content package>`), then `release.py android --apk ... --sdk ... --out <release folder>` ([android.md](android.md)). **Done:** the key is the maintainer's existing release key, the one of his other game, and `release.py android` passed. The key is not in the repository.
8. **The sums.** `release.py sums <release folder> --check`. For the files of the GitHub Release (step 9) the `SHA256SUMS.txt` was made with `sha256sum`, because `release.py sums` only knows the versioned names.
9. **The GitHub Release**, made by hand: the archives, `SHA256SUMS.txt`, and `LICENSE` and `NOTICE.md` beside the APK. No workflow does this. **Done for the Windows, Linux and Android files**, published under fixed names so that the README's `releases/latest/download/<name>` links work: `MagicPortals-Windows.zip`, `MagicPortals-Linux.tar.gz` and `MagicPortals-Android.apk` (a copy of the release APK under a new name; its contents are unchanged). The repository is private, so the Release is not public.
10. **A try on a PC that is not the maintainer's.** Not done for any platform.

## Once, before the repository is public

* **Visibility** (Settings, *General*). Nothing here changes it.
* **The triggers.** The workflows run on a dispatch and on nothing else. A push and pull-request trigger for `ci.yml` is a change of the file and of rule W01 in `tools/ci/check_workflows.py` ([ci.md](ci.md) section 2).
* **The licence.** `LICENSE` is the MIT No Attribution text, the same as the engine's, proposed in planning step 210 until the maintainer confirms or replaces it. `NOTICE.md` carries the licence texts of what the game contains.
* **The owner's files.** `python tools/ci/check_public.py` prints every finding in the files that only the maintainer changes (`OWNER_FILES` in the tool) as OWNER-FILE, with its lines. They are the maintainer's to read and decide; no tool or step here edits them.
* **The records.** The same output counts the paths of the maintainer's PC in `DEVLOG.md`, `docs/parity-backlog.md`, `docs/planning/` and `CLAUDE.md` (RECORD-PATH). Keep them, rewrite them, or squash the history: the maintainer's choice, and nothing here rewrites history. `python tools/ci/check_public.py --history` lists what past commits hold (it takes a few minutes) and removes nothing.
* **The contact for security reports.** `SECURITY.md` has one placeholder line for it; switch on private vulnerability reporting for the repository.
* **The repository's description and topics** (Settings).
* **The README.** Its front now has download buttons that point at the fixed file names of the Release (step 9). Read the front once more as a stranger would, and check those names against the Release when the repository is public: nothing here has followed the links as a stranger.

## What has never been done

A dispatch of `ci.yml` or `android-emulator.yml` (`release.yml` has been dispatched: [ci.md](ci.md) section 9); the Windows program that CI built started on any PC; a release archive on a PC that is not the maintainer's; the release APK installed on any device or emulator; the Android crash-report dialog on any device; a program on a real Mac, iPhone or iPad (the macOS and iOS archives with the game were not made); a phone's speed, memory and heat; code running on a 32-bit ARM device; real two-finger play; sound off Windows; a Vulkan 1.1-only driver; the Apple signing identities (the Android release APK was signed with the maker's existing key, which is not in the repository); the choice of the Windows C++ runtime (carried or asked of the player), the application ids, the version number (the first release used the one the project defines) and the icon.
