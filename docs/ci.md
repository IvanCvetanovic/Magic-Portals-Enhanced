**The driver: what it is, and why this one.** Mesa's lavapipe (the software Vulkan driver, Mesa's own, on the CPU through LLVM) built for Windows by the **build-mesa** project (`mmozeiko/build-mesa` on GitHub), release **26.2.6** (tag `26.2.6`, published 2026-10-29), asset `mesa-lavapipe-x64-26.2.6.7z` at `https://github.com/mmozeiko/build-mesa/releases/download/26.2.6/mesa-lavapipe-x64-26.2.6.7z`: 13,021,846 bytes, **sha256 `4ed980046a8d42de4efa74085f00e238a51c774b854d63ecece6dfee59ab3bf3`** (the value GitHub lists for the asset, and the value computed here from a download on 2026-11-17: they are the same). RUN here on the maintainer's PC, nothing started: the archive holds exactly two files, `vulkan_lvp.dll` (55,275,008 bytes; a 64-bit DLL whose imports, read with `dumpbin /dependents`, are only `KERNEL32`, `USER32`, `GDI32`, `SHELL32`, `ole32`, `ADVAPI32`, `ntdll` and one `api-ms-win-core` stub: it is statically linked, so no Visual C++ runtime or LLVM DLL is needed; its exports are the loader's driver entry points `vk_icdGetInstanceProcAddr`, `vk_icdNegotiateLoaderICDInterfaceVersion` and `vk_icdGetPhysicalDeviceProcAddr`; its text holds `VK_KHR_win32_surface` and `Mesa 26.2.6 (LLVM 23.1.4)`) and `lvp_icd.x86_64.json` (`"api_version": "1.4.354"`, `"library_path": ".\\vulkan_lvp.dll"`, relative to the manifest, so the two files can sit in any folder). The driver names its device `llvmpipe (LLVM ...)`, and writes its own version as Mesa's three numbers packed into the Vulkan way, `(26 << 22) | (2 << 12) | 6`, which the engine's `GPU offered:` line should print as `driver 0x6802006` (derived from that packing rule and NOT yet seen in any log; only `llvmpipe` is required of the log; `tools/ci/test_check_workflows.py` holds the number to the pinned version).

**What could rot, and what it looks like:** a release or asset that is deleted or replaced makes the download fail or the sha256 differ, and the step says so (`the lavapipe archive is not the pinned one`) and unpacks nothing: it is never silent. GitHub lists no licence for the repository (what is built is Mesa and LLVM); its maintainer can delete the repository. A Mesa and LLVM pair can regress: the notes of `mesa-dist-win` for its 26.0.5 and 26.0.6 say "lavapipe crashes at runtime if linked with LLVM 22", and this build is linked with LLVM 23.1.4: whether it runs on a runner's CPU is NOT KNOWN. To move to another release: change `LAVAPIPE_VERSION`, `LAVAPIPE_URL` and `LAVAPIPE_SHA256` together (the tests tie the URL to the version and the number the log must show to the version), compute the sha256 from your own download and compare it with the one the release lists, and change the three places of this section.

**How the loader is told where the driver is, and why twice (READ from the Vulkan-Loader documents and source; NOT KNOWN on the runner).** A Vulkan loader on Windows IGNORES `VK_DRIVER_FILES` and `VK_ICD_FILENAMES` in a process of high integrity (`docs/LoaderDriverInterface.md`, "Exception for Elevated Privileges"; the source: `loader_secure_getenv` returns nothing when the process token's integrity level is `SECURITY_MANDATORY_HIGH_RID` or more), and it reads the drivers of the registry key `HKLM\SOFTWARE\Khronos\Vulkan\Drivers` (one value per manifest, named with the manifest's full path, data 0) whatever the process is. GitHub's Windows runner is believed to run its steps as an administrator (not read from a source here), and **whether its steps are of high integrity is NOT KNOWN here**; so the step does both, the `Runner` step and the driver step print the integrity level as a SID (`S-1-16-8192` medium, `S-1-16-12288` high), and the fixture runs do not trust either: they require the game's own line `Selected Physical GPU: llvmpipe`. If the variables count, the registry is not read for drivers (the variables name the only driver); if they do not count, the registry names it. With `VK_LOADER_DEBUG` the loader writes `Loader is running with elevated permissions. Environment variable VK_DRIVER_FILES will be ignored` when it ignores them.

**The loader itself.** The program imports `vulkan-1.dll` and loads it late (the release program delay-loads it; `check-program` requires that). `windows-2025-vs2026` has one in `System32`: the CMake configure of its Windows jobs requires it (`engine/CMakeLists.txt:150`) and passed in `release.yml`'s second dispatch (section 9). Its VERSION is NOT KNOWN (the `Runner` step prints it); the loader that ships with the Mesa build does not exist (the archive has two files), nothing copies a loader next to either program, and the release program does not bundle one. If a later image lacks it, the CMake configure of this job stops first; a LunarG runtime would then be the fix, and none is pinned.

**What the fixture steps assert, and what they cannot.** That the program started, drew 300 fixed ticks and wrote a picture of at least 640x360 that is not one flat colour (a window may be made smaller than asked; the Linux jobs use the same checker and floor), and that the game's own log names llvmpipe as the GPU it selected. They cannot say the picture is RIGHT or that a real GPU works.

**What to read first in the first run's log** (artifact `windows-logs`: the log files and `shots/`; the steps' own output has the same):

1. `Runner`: the FileVersion of `vulkan-1.dll`, and `integrity level of the steps: S-1-16-...` (and which tools `command -v` found: `7z`, `timeout`, `curl`, `sha256sum`, `cygpath`).
2. `Software Vulkan driver (lavapipe, pinned)`: `.../lavapipe-26.2.6.7z: OK` from `sha256sum`, the two files listed by `ls -l`, the manifest, the `reg query` output (it must list the manifest's path), and a `::warning::` if the registry write was refused.
3. `Run the fixture`, in the group `everything the program and the loader wrote`: the loader's lines about the driver (`Found ICD manifest file`, `Loading driver library`, or the sentence about elevated permissions), then `GPU offered: llvmpipe (LLVM 23.1.4 ...), Vulkan 1.4.354 ... driver 0x6802006` (all expected, none seen yet) and `Selected Physical GPU: llvmpipe`, then `finished: clean` and the exit code. If the loader found no driver the game stops with a `fatal:` line (`Failed to find GPUs with Vulkan support!`, or an error of the instance's creation: which one is NOT KNOWN) and exits 1.
4. The two pictures in `shots/`.
5. `Run the fixture from the archive` and `Run with no game data`: the same, for the shipped program; the warning of the last one says whether a program with no console can write to a redirect.

**The likeliest failures of the first run, in order** (a guess, not a measurement):

1. **The loader does not find the driver** (a `fatal:` line about GPUs or the instance, or a GPU other than llvmpipe): the variables are ignored AND the registry route failed (an old loader that cannot read the manifest, a refused write); read the loader's lines in the group, and the `reg query` output.
2. **The shipped program's first start ever:** it has never been started on any machine that this repository knows. A missing Visual C++ runtime DLL (the archive does not carry one; the image has Visual Studio, which installs it) makes Windows show a modal box that nobody closes: the launch's `timeout 300` and the step's `timeout-minutes` end it, and the log is empty. A window that cannot be created on the runner's desktop, or a surface the driver refuses, shows as a `fatal:` line in the program's own log and a `MagicPortals.exe` exit code of 1.

## 8. The public-readiness check (planning step 210, PORT-12)

`python tools/ci/check_public.py` reads the files git tracks (`git ls-files`, so it gives the same answer in a clean clone, where `out/`, `reference/` and `build/` do not exist) and prints a table of findings with a class, a rule, a place and a sentence. It exits 1 when there is a finding of class ERROR and 0 otherwise. It changes nothing and fetches nothing; standard library and git only. `ci.yml`'s `tools` job runs it. **Whether that step works on a runner is NOT KNOWN:** `ci.yml` has not been dispatched (sections 2 and 9).

| Class | Meaning | Exit |
|---|---|---|
| ERROR | a defect of the files a stranger reads | 1 |
| RECORD-PATH | a path of the maintainer's PC inside a record file (`DEVLOG.md`, `docs/parity-backlog.md`, `docs/planning/`, `CLAUDE.md`): counted per file and listed by line; a record says what was true when it was written | 0 |
| OWNER-FILE | a finding in a file only the owner changes (`OWNER_FILES` in the tool: `CLAUDE.md`, one file of `docs/`, `.gitignore`, `.gitmodules`): listed with its lines, never edited by the tool | 0 |
| NOTE | a fact the owner should see: the ten largest files, an e-mail address, an allow-listed file, the one allowed placeholder, a record file's wording | 0 |
| HISTORY | something in a past commit (only with `--history`); nothing is removed by anyone for it | 1 |

**The rules** (each has a test that passes a synthetic repository and fails an edited copy of it, `tools/ci/test_check_public.py`): H1 no tracked file with the extension of a picture, sound, binary, package, key or original-game data file; H2 no NUL byte (a binary) and no file over 8 MiB; H3 no key or token shaped text (a PEM private key, GitHub and AWS tokens, a Slack token, a keystore password written as a literal; Android's published debug keystore password is allow-listed by name, with its reason printed); H4 no path of the maintainer's PC (a Windows user folder, `/home/<name>`, `/Users/<name>`, a drive mounted under `/mnt`) and not the name of the account that runs the check, which is read from the system when it runs and is never printed (a name of five letters or more is looked for anywhere, even glued to letters or digits, as the program check does; one of four letters as a whole word; a match that lies inside an e-mail address of a person is reported by the e-mail note instead, so an ordinary address of the maintainer that starts with the name is a note and not an error; a placeholder address and a GitHub noreply address are not addresses of a person for this rule and are hits); H5 none of a list of phrases the project keeps out of its files (`KEPT_OUT_PHRASES` in the tool), and the one placeholder line of `SECURITY.md` nowhere else; H6 `.gitignore` still has its `reference/` line, the comment block above it (at least 25 comment lines, the file has 30, and the block still says "DELIBERATELY EXCLUDED" and "DELIBERATELY UNANCHORED") and no line that unignores anything under it; not the engine's README) names a heading that exists in `README.md`; H12 `tools/package/check_version.py` passes.
