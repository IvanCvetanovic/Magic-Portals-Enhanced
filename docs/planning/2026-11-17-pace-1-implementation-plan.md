## 1. DECISION SUMMARY

**The mechanism, in plain words.** The port keeps its 60-ticks-a-second engine tick, its one solver step per tick, its 16 ms script clock and its 16.7 ms input grid. `clock.json` gets ONE new key, `original_frame_hz`: the frame rate of the original that the world stands for (60 = today's pace = the original on a 60 Hz screen; 30 = the owner's videos). From it the clock derives `frameTicks = matched_hz / original_frame_hz` (1 now, 2 flipped) and the physics seconds one tick advances, `simS = physics_step_s / frameTicks`. At 30 that is exactly the float 1/60 [v-calc: `0.03333333507180214/2 == double(float(1/60))`], so `SimRatio` is exactly 1.0 and every body falls, swings and recoils in real time with no per-body edit: the player at 1000 u/s^2, knights/stones/crates at 500, zero-g recoil at 70 u/s. Everything the original multiplies or delays once per FRAME (a frame is now two ticks) goes through named rules in `ScriptClock` (identity at one tick a frame); everything the original judges per ORIGINAL STEP (the translation clamp, the impact reader's Box2D replay) is judged on `frameTicks` ticks. The plumbing lands first, on `main`, inert, with a byte-identical 129-plan trace digest; then, on a separate worktree branch `pace-30`, the FLIP is ONE small commit (a data value and the compiled default), followed by pin repairs written as closed-form literals, the physics candidates, **a hand-play checkpoint on the owner's phone**, a FREEZE of every physics input, and only then the re-time of the 129 plans.

## 2. MECHANISM, EXACTLY

### 2.1 The clock model (vocabulary used everywhere below)

| Term | Definition | Today (neutral, `original_frame_hz` 60) | Flipped (30) |
|---|---|---|---|
| tick | one engine fixed update, `MagicPortalsLayer::kTick` = `1.0f/60.0f` [v game/MagicPortalsLayer.hpp:140 per [CR1]; the rigs step `PhysicsSystem::Update(kTick)` once per tick: v tests/test_mp_routes.cpp:211, :671; game/sim/Game.cpp:1159-1160] | 1/60 s | unchanged |
| original frame | one update of the original at `original_frame_hz`; `frameTicks = matched_hz / original_frame_hz` ticks | 1 tick | 2 ticks |
| frame phase | `Step::framePhase` = (number of `stepLevel` calls made so far in this level) mod `frameTicks`; 0 = the first tick of a frame. The counter is a NEW layer member `m_levelStepCount`, reset where `m_levelAgeMs` is reset [v game/MagicPortalsLayer.cpp:1314], and incremented at the TOP of `MagicPortalsLayer::stepLevel` [v :14564], which has FOUR call sites [v :14305, :14316, :14540, :14559]. It is NOT advanced beside `m_levelAgeMs += dtMs` [v :14529]: a pause or popup tick returns before that line and its resume tick calls `stepLevel` without it [v :14299-14306], so an age-paired counter would repeat a phase across a resume (critique C1-13). It is NOT `LayerTicks()`/`m_ticks`, whose only change is `++m_ticks` [v :14272] and which never resets. | 0 | 0,1,0,1,... |
| `simS` | the original's physics seconds ONE TICK advances = `Rules::physicsStepS / frameTicks`; `physicsStepS` is the decoded `physics_step_s` 0.03333333507180214 = the float 0x3D088889 [v game/data/clock.json:47], never edited | 0.03333333507180214 | 0.01666666753590107 (= `double(float(1/60))`; halving a float is exact [v-calc]) |
| `SimRatio` | `simS / physicsS` [v game/sim/ScriptClock.hpp:102-104] | 2.0 | exactly 1.0 (`==` pin) |
| `scriptS` | exact whole ms a tick hands the scripts = `floor(1000/matched_hz)/1000` [v ScriptClock.cpp:47, :66] | 0.016 | 0.016 (96 % of real time; waived, 2.3 g) |
| `fps` | what `GetFPSRate` answers = `original_frame_hz` (today `matched_hz`; the same number at 60). `Step::fps` has NO consumer in `game/` today [v `grep -rn "\.fps" game` finds none outside ScriptClock] except through `Player::AirShare` (2.3 a) | 60 | 30 |
| wall clock | `WallMs(step)` = `physicsS x 1000` [v ScriptClock.hpp:138] | 16.667 ms | unchanged |

`matched_hz` stays the TICK rate (60): it drives the script floor (16 ms) and the engine-facing contracts. `original_frame_hz` is the ONLY pace knob. Compiled default `ScriptClock::Rules{}`: `originalFrameHz = 60`, `frameTicks = 1` (so the pure suites that default-build Rules keep certifying today's reading until S10 moves the default to 30 in the same commit as the file). `Rules` gets `bool SetOriginalFrameHz(int hz)`, which validates (below) and sets `originalFrameHz` and `frameTicks` TOGETHER, so a pure suite that builds a `Rules` in code (S8's pure rows) cannot set one without the other. `LoadRules` treats an absent key as `matched_hz` (neutral), reads whole numbers only, and refuses `original_frame_hz` that is below 1, above `matched_hz`, or does not divide `matched_hz` (45, 0, 61, 120 are refused naming the key: J2's `max(1, lround)` silently turning 45 into 1 is the reason).

`Step` (ScriptClock.hpp:75-91) gains `int frameTicks = 1` and `int framePhase = 0`, as defaulted TRAILING parameters of the 4-argument constructor (every existing brace/positional call stays valid); a bare `Step(float)` is frameTicks 1, SimRatio 1, exactly as the pure suites mean it today. There is NO new double field (v1's `originalStepS` is dropped: it equals `physicsStepS`, a Rules constant). `TickStep(rules, physicsS, unsigned levelStep = 0)` fills `frameTicks`, `framePhase = levelStep % frameTicks`, `simS = rules.physicsStepS / frameTicks`, `fps = originalFrameHz`; the two layer calls [v MagicPortalsLayer.cpp:436 (constructor, passes 0) and :14209 (`OnFixedUpdate`, passes `m_levelStepCount`)] are the only callers.

The one helper that carries the "per ORIGINAL step" quantities (critique C1-12: v1 implemented it as `originalStepS / SimRatio`, which is not bit-exact for a hand-built ratio such as `Step(1.0/60, 1.0f/60, 1.0/30, 60)` [v tests/test_mp_demolish.cpp:1074], ratio 1.99999995 [v-calc]):
```
// ScriptClock.hpp: the original's physics step, in the seconds the port's carried velocities are measured in
inline double OriginalStepCarriedS(const Step& s) { return static_cast<double>(s.frameTicks) * static_cast<double>(s.physicsS); }
```
Exact at every frameTicks (an integer times a double; 1 returns `physicsS` bit for bit = today's `static_cast<double>(step.physicsS)`; 2 is an exact doubling). A hand-built step keeps frameTicks 1, so the clamp and the Impacts replay read today's value bit for bit. The division form `rules.physicsStepS / SimRatio(step)` survives only as a test ORACLE (relative tolerance 1e-12) for TickStep-built steps.

### 2.2 The helper API for once-a-frame quantities (named, classed)

All in `ScriptClock.hpp`, pure, header-only, each with a closed-form oracle in the new `tests/test_mp_frameclock.cpp` and **identity at n = 1** (early return of the input: no `pow`, no rounding; J1's `1-(1-0.3)/1 = 0.30000000000000004` is why v1's `FrameDrag` was dropped: it has no consumer).

| Class | Helper | Use it when | Consumers (this plan) |
|---|---|---|---|
| **T** per-tick, solver-paired | none (value unchanged) | the original multiplies a velocity the solver re-drives once per step; the contact equilibrium is per step | knight Hold brake 0.3 (`Minions.cpp:803`) by default; Impacts' classification window `kRecentSteps` and Boss `recent_ticks` (solver steps) |
| **V** distance-preserving share | `FrameTravel(s, n) = n s / (1 + (n-1) s)` | a free velocity multiplied once a frame by `s` whose summed TRAVEL places a landing: per-tick share `r` with `r/(1-r) = n s/(1-s)` | the air brake, form `travel` (default of the flipped data) |
| **R** decay-preserving share | `FrameRoot(s, n) = s^(1/n)` | the value at each frame boundary must equal the original's; no travel at stake | the air brake, form `root` (alternative); cosmetic decays in S14: key scale 0.9, crystal timer, ghost-appear `scale_per_frame` 1.005 |
| **D** delay | `FrameDelayTicks(frames, step) = lround(frames x frameTicks)` (half away from zero: 2.25 -> 5, 2.5 -> 5 [v-calc]; Python's `round` would give 4: the test pins C++ `lround`) | the original reads a state `frames` frames old | the ground-flag lag; any half-frame ordering site that a measured plan proves decisive (DM-10) |
| **G** phase-gated | `step.framePhase == 0` | an integer-truncating decay, or a write the original makes once per frame | level-end pad alpha byte (S14); the knight Hold brake, the pad's x write and the shot's static pass ONLY if DM-4/DM-5/DM-12 rule so (S9) |
| **O** original-step | `OriginalStepCarriedS(step)` | the original judges per ORIGINAL step | translation clamp; Impacts' Box2D replay (via `FreeFlightRules::frameTicks`) |
| **W** wall | `WallMs(step)` | `sys:GetTime` readers | unchanged (2.3 h) |

(PACE-30's S/V/O letters classified ORDERING SITES; they are not used here. A site becomes class D only when DM-10 proves it decisive.)

Oracles (test names in 7): `FrameTravel(0.43, 2) = 0.86/1.43 = 0.601399`; the tail after a release at 2.4 u/tick = `2.4 x 0.601399/0.398601 = 3.621` u against the original's `4.95 x 0.43/0.57 = 3.734` u per 4.95 u frame [v-calc] (the 3 % difference is the walk's 144 vs 148.5, 2.3 g); `FrameRoot(0.43,2)^2 = 0.43` (0.655744); `FrameRoot(0.9,2) = 0.948683`; `FrameTravel(1,n) = 1`, `FrameTravel(0,n) = 0`; all helpers equal their input at n = 1.

## 5. THE RE-TIME TOOL AND METHOD

### 5.1 What a plan is, what is frozen, what moves
A plan (`tests/routes/levelNN.json`, `tests/routes_gold/level20b.json`) is `level`, `win_by`, optional `medal`, `holds` `[{walk: left|right, from, to}]` and `taps` `[{tick, release?, at: [x, y], shot?, drag_to?}]` [v game/Route.hpp:69-100: `Hold{from,to,direction}`, `Tap{tick, releaseTick, atPx, shot, toPx}`; game/Route.cpp:122, :148, :176]. **Frozen, never touched by the retimer** (critique C2-17: v1 named only the `at` point): every tap's `at` point, **`shot` flag, drag target `drag_to`, and `release - tick` (the shot's aim hold; a drag's finger speed)**; the taps' count and order; every hold's `walk` direction and the holds' order; `level`; and any existing `medal` pin (the owner's: 8 FILES today [v grep above], 7 in `tests/routes` and `routes_gold/level20b`). The controls census (`tests/golden/controls_census.json`: 128 routes, 688 shot taps, 611 on gravity levels [Rt]; it reads exactly the taps with `shot` true and their points [v tests/test_mp_census.cpp:168-169]) is the owner's. `routes_gold` is outside it. **Moves:** each tap's `tick` (and its `release`, by the same amount), each hold's `from`/`to`, `win_by`, and the new `pace_hz` and `_pace` note. `plan.py`'s frozen-field guard refuses a plan whose frozen fields differ from the source plan's.

### 5.2 Why the warp is anchored on events
Physics waits double in ticks (falls, landings, swings, flings, stone and crate settling, zero-g drift); real-time waits do not (walks, a shot's flight at 192-200 u/s, the 400 ms cadence of about 25 ticks between shots, knight holds, door timers). A blind seed that stretches idle gaps cannot tell them apart by length: identity 58 wins / 55 same medal / 36 same sounds; every gap x2 60 / 56 / 33; gaps of 12+ ticks x2 64 / 60 / 36 with a median win-tick shift of +214 [LV, own negative result]. So the warp pairs EVENTS.

### 5.3 The pipeline, per level, unattended (`tools/parity/retime/retime.py level <name> --profile final --budget N [--goal win|drop217|drop321]`)
Oracle = the real `test_mp test_mp_routes --only <abs plan> --trace 1` through `rig.py` (env `MP_DATA_DIR`/`MP_PORT_DATA_DIR` = the staged tree of the final profile, or none after the freeze), run inside ONE X session by the driver (3.13); a rig error (nonzero exit, timeout, lock) is retried once and then reported as a RIG ERROR, never as "stuck". Every hill climb logs its random seed. After the freeze `retime.py` and `install.py` check `freeze.json` (S12b).
* **R0 classify** against S0's reference: SAME (same win-tick class, medal and multisets), LATE (same medal, later: extend the last hold, raise `win_by`; 10 plans at the lever, e.g. level8c 91 -> 153, level5c 181 -> 331 [Rc]), or FAIL.
* **R1 event warp.** Events from the trace: `sound <name> [at volume V] on tick N` (not `shot_fired`: the taps themselves), `resting: <sleeper> asleep on tick N`, `door <name> opening|closing on tick N`, `wall contact: ... on tick N`, `minion_fell`, `player_fell` [regexes proven in the prototype, `pace_tests/retime.py:parse`, lines 32-63]. Pair the old run's events with the new run's by (name, occurrence); move every key by the shift of the LAST paired event at or before it (its delay after that event stays what it was); replay; the run gets further, more events pair; repeat from the ORIGINAL plan to a fixed point (2-5 replays; 14 of the 31 repairs at the lever were this alone [Rt]).
